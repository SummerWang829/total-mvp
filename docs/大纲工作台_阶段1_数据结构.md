## 1. 条目的两种编号（补充 3）

- **内部编号 `item_uid`**：条目创建时生成，**永远不变**，复制到新版本时也不变。
- **显示题号 `label`**（H1、C2…）：可以改。
- 笔录句、标记、编码回答、关注问题**只存 `item_uid`**，显示时再按当前版本换成题号。改题号不会让历史记录对不上。

## 2. 新建的表

| 表 | 存什么 | 关键字段 |
|---|---|---|
| `outlines` | 一个项目可有多份大纲 | 项目、名称、当前版本 |
| `outline_versions` | 大纲版本 | 版本号、状态（草稿/已发布）、基于哪一版、改动摘要、`rev`（修改次数）、创建人和时间 |
| `outline_items` | 条目（题目和物料同一列表） | 版本、`item_uid`、`label`、模块、顺序、类型（题目/说明/概念卡/视频片段/网站任务/打分题）、zh/en/ms/ta 文本、追问列表、必问要素、服务的关键问题、对应假设、预计分钟、是否备选、类型配置 |
| `outline_snapshots` | **大纲快照（补充 1）** | 版本、`rev`、内容（条目全文 + 设定摘要）、内容哈希；同一个（版本，修改次数）只存一份，多场共用 |
| `materials` | 物料素材，可被多份大纲引用 | 项目、类型、存储位置、预检结果、语言版本 |
| `study_settings` | 研究设定（生成大纲的中间结果） | 背景原文、13 个槽位（值、来源=原文/推断/默认/项目设置、把握）、业务决策、关键问题、假设、**流程进度（补充 8）**：三轮各自的作答状态、三道关口是否确认 |
| `revisions` | 修订 | 大纲、基于版本、目标条目、操作、改前、改后、理由、时长影响、质检结果、去向（大纲/物料/主持引擎）、来源、提出方、状态、决定人和时间、**`train_case_id`（补充 7）**：去向为“主持引擎”时写入训练集的用例编号 |
| `marks` | pilot 标记 | 场次、笔录句、`item_uid`、引用原文、句内起止、标签、意见、作者、作者角色、**状态（待处理/已解决）和 `resolved_revision_id`（补充 6）** |
| `focus_questions` | 关注问题 | 项目、文字、提出人和角色、时机、`item_uid`、编码方式、编码表、从哪一场开始问 |
| `coded_answers` | 编码回答 | 关注问题、场次、笔录句、来源（被问到/主动提到）、**`mentioned_in_item_uid`：主动提到时是在哪道题里说的（补充 5）**、编码、把握值、编码方（AI/人）、是否人工确认、**`ai_code`：AI 的原编码，人改后保留（补充 5）**、`clip_id`（补充 10，指向洞察里已有的片段，不新建） |
| `host_decisions` | AI 主持决策记录 | 场次、笔录句、原因、饱和度、未覆盖的必问要素 |
| `rehearsal_runs` | 模拟预演结果（补充 9） | 大纲版本和修改次数、场数、时长、必问覆盖、发现的问题、`eval_report`（现有评估报告文件名，复用其 JSON 格式） |

## 4. 规则

1. **不锁定（用户选 B）。** 版本随时可改，每改一次 `rev` +1；已有场次用的版本，界面提示“这份大纲已被 N 场使用”。
2. **快照（补充 1）：** 场次开始时，把当时（版本，`rev`）的大纲内容存成快照（已存在就复用），并把版本号、`rev`、快照编号记在场次上。**进行中的场次全程用快照，中途改大纲不影响它；AI 主持引擎也从快照读配置**（`ai_room.project_guide()` 优先读场次的快照，没有快照的老场次走旧路径）。
3. **修订只能由人接受。** AI 只产生“待定”修订；服务器校验：条目存在、类型匹配、每次最多 3 项；质检不过（碰红线）的不能接受；客户角色不能接受；去向为“主持引擎”的必须带 `train_case_id` 才能接受。
4. **人工主持挂题号（补充 2）：** 主持人在房间的大纲里点“正在问这一题”→ 记为 `host`；没点则自动猜，记为 `guess`：**结合题目在大纲里的先后顺序（当前题和下一题加分，往回跳减分）加文字相似度**，不够把握就不挂；研究员可事后在笔录里改题号（记为 `edited`）；看板统计里 `guess` 的要标出来。AI 主持的场次直接挂（`ai`）。
5. **AI 原编码（补充 5）：** 人改编码时，`ai_code` 保留原值，用来校准。
6. **旧结构：** `Project.outline_text`、`outline_versions`、`outline_chat` 保留到阶段 2 结束，之后随旧大纲页面和接口一起删除（用户决定不迁移旧数据）。
7. **“加入报告引用”（补充 10）：** 接到洞察里现有的片段（`clips`）和引用（`evidence`），不新建一套；阶段 1 只在编码回答上留 `clip_id`，真正的接线在阶段 4。
8. **模拟预演的存法（补充 9）：** 评估报告现在是仓库里的 JSON 文件，没有租户字段，不适合直接存多公司数据；所以预演结果存数据库一行，并记下对应评估报告文件名，报告内容仍用现有格式。

## 5. 阶段 1 结束时附的演示数据脚本（补充 11）

`scripts/outline_wb_demo.py`：按原型“A 品牌进入新加坡”的例子，往指定项目（或第一个项目）里生成：
- 一份完整大纲（含概念卡、视频片段、网站任务、打分题）；
- 两场 pilot 笔录（已挂好题号、带 AI 决策记录）；
- 一些关注问题和编码回答（含“被问到”和“主动提到”）。
阶段 2 做界面时直接用。演示数据全是虚构，不含真实姓名和联系方式。

## 6. 测试（只测这一阶段）

每张新表的增删改查；`rev` 递增；场次记版本号、`rev`、快照；**快照在大纲改动后保持不变**；同一（版本，`rev`）只存一份快照；**改题号后，历史笔录、标记、编码回答仍对得上**；**AI 原编码在人工修改后保留**；修订只能由人接受、红线不过不能接受、客户不能接受、主持引擎去向要有用例编号；自动猜题号会参考顺序；标记的状态和解决修订；新表并入保留期清理；迁移重复执行不出错；租户隔离。
不测：界面、AI 模型调用、实时推送（后面阶段）。
