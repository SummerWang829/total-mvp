## 2. 现有表新增的列

| 表 | 新列 | 说明 |
|---|---|---|
| `interviews` | `outline_version_id`、`outline_rev`、`is_pilot` | 场次开始时记下用的大纲版本和它当时的修改次数；pilot 标记 |
| `caption_lines`、`transcript_segments` | `item_code` | 这句话对应的大纲条目编号（H1…），pilot 圈改和看板都靠它 |

## 3. 规则

1. **不锁定（用户选 B）。** 任何版本随时可改；改一次 `rev` 加 1；如果这个版本已有场次，界面提示“这份大纲已被 N 场使用”。
2. 场次开始时存 `(outline_version_id, outline_rev)`。因此即使大纲后来被改，分析时仍能区分“改之前问的”和“改之后问的”。**这是我在 B 之上加的一个小保护，需要你确认。**
3. **修订只能由人接受。** AI 只能产生“待定”修订；服务器校验：条目存在、类型匹配、每次最多 3 项；质检不过（红线）的修订不能接受。客户角色只能圈、写意见，不能接受。
4. **新结构取代旧结构。** `Project.outline_text`、`outline_versions`、`outline_chat` 字段保留到阶段 2 结束，之后随旧大纲页面和接口一起删除（用户决定不迁移旧数据）。`ai_room.project_guide()` 改读“已发布版本”。
5. 笔录句的 `item_code` 实时写入：房间里 AI 主持人当前问的是哪道题就挂哪道；人工主持的场次由主持人点题时挂上。**人工主持怎么挂，我还没想清楚，列入下面的问题。**

## 4. 阶段 1 的测试（只测这一阶段）

每张新表的增删改查；`rev` 递增规则；场次记版本号和修改次数；修订只能由人接受、红线不通过不能接受、客户不能接受；新表并入保留期清理（到期后删净）；迁移重复执行不出错；租户隔离（所有查询带 `org_id`，越权返回 404）。
