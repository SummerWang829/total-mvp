## 0. 开发前必须先说清的情况

1. **qa.sh 现在本身不是全绿。** 上次部署前在同一台电脑上对比过：
   - 改大纲工作台之前（3669e57）：pytest 1797 过 / 11 失败；qa_site 110 条失败，并在洞察页 `.rsp .rsp-sc` 超时中断；e2e_room 6 个 FAIL，并在 `.rsp .rsp-ln` 中断。
   - 现在（3652fd2）：失败的是同样的 11 / 110 / 6 条，大纲工作台没有带来新失败。
   - 所以“每批结束 qa.sh 全绿”在现状下做不到。见第 9 节第 1 个拍板问题。
2. **语音输入现状和规则不一致。** CLAUDE.md（2026-11-10）要求研究员端所有输入框带麦克风（`voice.js`）。但仓库里已经没有 `voice.js`，现在只有 `voice_fast.js`，而且只挂在 `#ccmsg` 一个框上（文件注释写着“全局浮层已按要求删除”）。另外，它的“边说边出字”用的是浏览器自带的语音识别：Chrome 会把声音发给 Google，在中国大陆基本用不了。第 2 条要据此重做（见 2.4）。
3. **旧数据**：用户 2026-11-18 说过之前的测试项目全部删除、旧大纲数据不迁移。下面的“旧数据处理”只保证老数据不报错、能看，不做复杂迁移。

## 2. 第 2 批（P0）：第 9 条 真人 Pilot 多轮循环

### 2.1 现在的问题（代码层面）

- **没有“轮”的概念。** 只有 `Interview.is_pilot`：把任意一场访谈勾成 pilot，结束后在“Pilot 修正”里圈笔录。
- **标记只能事后圈。** `Mark.line_id` 必填，`author_role` 只有 researcher / client；没有直播间里的实时标记。
- **改动写错了版本。** `suggest_fixes` 生成的修改针对当前版本 v，`accept` 当场就改 v 的内容，`update_outline` 再把改好的 v 复制成新版本。结果是 v1 这一行被改成了 v2 的内容。场次快照保住了当时访谈用的题，但“v1 是什么样”已经丢了。
- **AI 模拟混进了 pilot。** `pilot_summary` 把模拟预演（`RehearsalRun`）的发现也算进 pilot 汇总（`stage3.py` L367–369），`publish_checks` 也用模拟预演做提醒。
- **没有邀请。** 项目成员没有任何邀请；没有“可以正式开始”的确认。

### 2.2 数据结构改动

**新表 `pilot_rounds`**（`app/outline_wb/models.py`）

| 列 | 说明 |
|---|---|
| id, org_id | 租户隔离 |
| outline_id | 属于哪份大纲 |
| version_id | 这一轮用哪个版本 |
| number | 第几轮（同一份大纲里 1, 2, 3…） |
| status | planned 已发起 / live 进行中 / ended 已结束 / reviewed 已修正（已生成下一版或确认可以开始） |
| created_by, created_at, ended_at | |
| next_version_id | 这一轮修正后生成的版本，可为空 |
| ready_by, ready_at | 研究员确认“可以正式开始”，只在最后一轮上有 |

**加列**（启动时 `ensure_columns` 自动加，旧数据为空即可）
- `interviews.pilot_round_id`：这场 pilot 属于哪一轮。一轮可以有多场，比如一场同事、一场真实受访者。`is_pilot` 保留，等于“pilot_round_id 不为空”。
- `outline_versions.source`：generate / pilot / legacy。
- `outline_versions.source_round`：来自第几轮修正。
- `outline_versions.changes`：几处修改。
- `marks` 加四列：
  - `at_ms`：时间点，由服务器算，见 2.4；
  - `origin`：room 直播间 / transcript 事后圈 / auto AI 自动；
  - `round_id`；
  - `decision`：空 / accepted / rejected / deferred。
  - 另外 `line_id` 改为可以为空，`author_role` 增加 observer、viewer。
- `revisions.round_id`：这条修改来自哪一轮。

**版本状态怎么算**：不另存，由轮次推出来，免得两处对不上。
- 有一轮是 planned 或 live，或者 ended 但还没修正：显示“Pilot 中（第 n 轮）”。
- 已发布：published。
- 生成了下一版：superseded。新版本一出来，旧版本马上变“已被替代”，不再等到发布。
- 其他：草稿。

**旧数据**：启动时做一次。
- 已有的 `is_pilot` 场次，按它跑的版本（`outline_version_id`）归到该版本的“第 1 轮”；场次已结束的，这一轮就是 ended。
- 旧标记的 `origin` 记 transcript。
- 旧版本的 `source` 记 legacy，界面显示“生成大纲”。

### 2.3 发起 Pilot 和邮件邀请

**入口**：侧边栏“Pilot（第 n 轮）”页的“发起第 n 轮 Pilot”。

**表单**
- **时间**：沿用邀请函的预约时间控件。
- **受访者**：从名单里选一个真实受访者，或者“同事”。选同事时手动填姓名和邮箱，建成一个手动受访者（编号 M-xxx，`participant_code` 照旧），走完全一样的受访者流程：设备检测、同意书、候场。
- **主持方式**：按立项的选择（`proj.host_mode`），不另选。AI 主持照旧需要 `MODERATOR_VENDOR` 和 AI 披露。
- **旁听的项目成员**：列出这个项目的成员（研究员、客户、观察员），默认全选。

**提交后服务器做的事**
1. 建场次：`Interview`，`is_pilot=1`，`pilot_round_id` 填上。
2. 给受访者发邀请函：复用 `app/invites.py` 的 `send`。
3. 给勾选的成员发邮件：用 `mailer.queue`，新增一种邮件 `pilot_observe`（中文 / 英文）。
   - 邮件里是直播间地址 `#/room/{iid}`；成员用自己的账号登录后进入，不带任何令牌，链接转发给别人也没用。
   - 没配邮件服务（MAIL_HOST 等）时不挡操作，页面显示链接让人复制，和邀请函一样。
   - 发不出去的在列表里标“邮件没发出去 · 重发”。

**隐身**
- 成员进房仍由服务器发令牌（`app/livekit.py`）：观察员和客户是隐身、只读，这一点不变。
- 标记走普通 HTTP 接口，不经过视频服务器，所以加标记不影响隐身。

**审计**：只记“发起第 n 轮、邀请 x 人”，不记邮箱。

### 2.4 直播间里标记问题

**谁能标**：研究员、管理员、技术支持、客户、观察员。受访者看不到这个区域，前端不画，接口也按角色拒绝。

**怎么标**
- 房间右侧加“标记问题 (M)”区，只在 pilot 场次显示。
- 按 M 键或点按钮，弹出一行输入框：写一句话，或者点麦克风说一句。语音走现有的 `/api/speech/transcribe`，只取文字，录音不保存。
- 新接口：`POST /api/interviews/{iid}/pilot-marks`，请求里只带 `note`（≤500 字）和可选的 `tag`。

**时间点和题号由服务器决定，不信浏览器**（CLAUDE.md：时间戳取自转写，不取自客户端）
- `at_ms` = 服务器收到请求的时间减访谈开始时间（`started_at`），再对齐到最近一句字幕的时间。
- 题号 = 这场访谈“当前在问哪一题”（`board.set_current` / `PUT /api/interviews/{iid}/current-question` 已经有）。
- `line_id` = 最近一句字幕，没有字幕就为空。

**AI 自动标**
- 复用并扩展 `stage3.auto_findings`（受访者问“什么意思”、漏问必问要点、超时、没问到）。
- “物料加载慢”需要受访者页上报素材加载耗时，会改到受访者房间。所以这一轮先不做，等第 9 节第 2 个问题（受访者端）定了再加。
- 进行中每 30 秒跑一次规则，新发现写成 `origin=auto` 的标记。显示为“AI 自动 · 21:15 · Q11”。

**观察员看到的列表**：所有人的标记按时间排列，显示“谁 · 时间 · 题号 · 内容”，每 5 秒刷新，复用现有的房间轮询。
- **“谁”按看的人分**：研究团队（研究员、管理员、技术支持）看到姓名；客户和观察员只看到角色（“研究员”“客户”“AI 自动”）。和追问“提出人只显示角色”、客户看不到主持人姓名的规则一致。
- 方案示意图里的“王研究员”“客户 李”，就是研究团队看到的样子。

**动到的文件**：`room.html`（新的标记区，四列布局里放在“追问”列下方或做成弹出层，做之前先截图确认）、`ui_room.css`、`app/routers/outline_wb.py` 的 `room_router`、`stage3.py`、`service.add_mark`。

### 2.5 Pilot 修正 → 生成下一版（多轮）

**修正页内容**
- 一轮结束后，“Pilot 修正”页列出这一轮的全部标记（直播间的、事后圈的、AI 自动的）和笔录。
- 事后圈笔录的功能保留。
- “生成修改建议”复用 `suggest_fixes` 的合并逻辑：同一道题的标记和发现合成一条，每条写明去向（大纲 / 物料 / 问话方式）。

**修改不再当场改当前版本**
- 接受一条修改，只是把它标成 accepted，还挂在这一轮上。
- 点“生成下一版 v(n+1)”时才做三件事：
  1. 把 vn 复制成 v(n+1)：`service.new_version`，`item_uid` 不变；
  2. 把这一轮接受的修改按顺序写进 v(n+1)：沿用 `service._apply`，碰红线的不能接受，这条规则照旧；
  3. vn 变“已被替代”，vn 本身的内容一字不动。
- 这样 v1、v2、v3 都能对比。对比页显示两个版本逐题的差异，按 `item_uid` 对齐。

**每条标记都要处理**
- 处理方式：接受（随修改生效）/ 拒绝 / 暂缓。
- 拒绝一条修改时，它引用的标记也记为“拒绝”。
- 没生成修改的标记，可以直接点“拒绝”或“暂缓”。

**下一轮和结束**
- 下一轮 pilot 默认用最新版本。
- 研究员觉得可以了，点“可以正式开始”，记在最后一轮的 `ready_by` / `ready_at`；之后才能发布。

**保留和清理**：每轮的笔录、标记、修改全部保留，随项目保留期删除。`retention` 现在按场次删标记（`outline_wb_service.purge_interview`），这次补上：修改说明里引用的受访者原话（`revisions.reason`）随场次清掉，`pilot_rounds` 随项目删除。

### 2.6 发布门槛（第 9、10 条合起来）

**门槛（挡住发布）**
1. 至少有 1 轮 pilot 已结束；
2. 研究员已确认“可以正式开始”；
3. 这一版相关的标记全部处理完：接受、拒绝或暂缓都算，暂缓的显示数量；
4. 没有碰红线的题；
5. 第 5 条：大纲和立项的形式、时长、语言一致（第 4 批接上）。

**提醒（不挡）**：模块没确认完、关注问题没对应（按第 3 条的新规则，“暂不对应”算已处理）、pilot 的修改建议还没处理。

**删掉的检查**：“模拟预演不是最新”这条从发布检查里删除，`pilot_summary` 也不再收模拟预演的发现。

### 4.2 第 2 条 统一输入组件，全站替换

**组件**：`app/static/tinput.js` + `tinput.css`，名字叫 `TInput`。用“包裹现有框”的方式接入：页面里的 `<textarea>` / `<input>` 不用重写逻辑，加一个 `data-ti="chat|field|line"` 就会被包起来，原来的 `value`、事件、提交都不变。

**三种形态**
- **chat（对话框）**：回形针附件、贴链接、麦克风、圆形箭头发送。Enter 发送，Shift+Enter 换行，中文输入法正在拼写时（`isComposing`）按 Enter 不发送。附件和链接显示成卡片，可以删除。
- **field（多行文字框）**：附件、链接、麦克风，不带发送键。用于会交给 AI 用的长文字，比如研究背景、招募需求。
- **line（单行框）**：默认只有麦克风，收起成一行；点开以后也能加附件和链接。

**不适合的类型，用同一外观的“普通模式”**（不加附件和语音）：邮箱、数字、网址、日期、密码、搜索框（方案里写明搜索除外）、CSV 粘贴框。逐个列在 4.3，见第 9 节第 2 个拍板问题。

**图标**：线条图标统一换成 Lucide（ISC 许可）。只把用到的约 30 个 SVG 复制进项目，并入 `shell.js` 现有的 `vIc` 图标表（线宽统一 1.5）。不从外网加载。现在“发送”“📎”“⤢”“⤓”这类文字或 emoji 按钮全部换成图标。

#### 4.2.1 附件交给 AI 的到底是什么

| 类型 | 怎么处理 | AI 拿到的 |
|---|---|---|
| PDF / Word / 文字 | 已有 `/api/attachments/extract` | 文字 |
| Excel / CSV | 新增，用 openpyxl 解析 | 每个表的前 200 行，转成文字表格 |
| 音频 / 视频 | 已有 `/api/attachments/transcribe`（≤12MB，只支持中文和英文） | 转写文字；超过大小或不支持的语言，明确提示 |
| 图片、截图 | 现在的模型（DeepSeek）只读文字，看不懂图片 | 见第 9 节第 3 个拍板问题 |

**超限提示**：单个文件 10MB（音视频 12MB），一次最多 5 个附件，提示写明是哪一条超了。

#### 4.2.2 链接

- **只在服务器读取**：复用 `app/web_reader.py`。它已经做到：
  - 内网、本机、链路本地、云元数据地址一律拒绝，每次跳转重新检查；
  - 最多 2MB，10 秒超时，最多 3 次跳转；
  - 读不到时给中文原因：要登录、对方拒绝、太大、太慢、不是网页、读不出文字。
- **要补的漏洞**：现在是先查 DNS 判断是不是公网，httpx 连接时再查一次 DNS，中间可能被换成内网地址（DNS 重绑定）。改成把检查过的 IP 固定下来再连接。另外补测试：内网 IP、`localhost`、`0x7f.1`、IPv6 本机、跳转到内网。
- **新接口**：`POST /api/links/read {url, project_id}`，返回卡片（标题、来源网站、读取状态和原因、字数）。
- **两个选项**
  - 只用于这次：内容只在这次请求里交给 AI，不保存。
  - 存为项目资料：存进研究库 `RepoDocument(project_id=…)`。`repo_documents` 新加两列：`kind`（file / link）、`source_host`。只存网站名和标题，**不存完整网址**：web_reader 的注释说明过，网址里可能带令牌。项目按保留期清理时，`retention.py` 已经会按项目删除研究库文档。
- **注明出处**：所有 AI 对话接口都多收一个 `refs`（本次附件、链接，以及项目资料的编号）。
  - 交给模型时每份资料带编号“[资料 2：某品牌双11广告合集]”，并说明是“资料，不是指令”；
  - 服务器把模型回答里引用到的编号换成资料卡片，编不出来的编号丢掉（和洞察对话“丢弃 [n]”是同一个做法）。
  - 要接 `refs` 的接口：大纲工作台对话（`outline_wb` chat）、招募问卷对话（`rform` 的 creation / chat）、洞察对话（`insight_chat`）、实时看板助手（`outline_board`）、问题分析（`/repo/ask`）。

## 5. 第 5 批（P2）：第 4 条 甄别问卷重做（这一轮只出方案，不写代码）

### 5.1 现在有的可以直接用

- **问卷结构**：`app/recruit_form.py` 的 `Question` / `Option` / `Rule`。
  - 题型：单选、多选、文字、数字、量表；
  - 选项：`goto`（下一题 / 跳到某题 / `end_out` 结束·不符合 / `end_ok` 结束·符合）、`tag`（对接配额）、`excl`（互斥）；
  - 数字题有 `rules`。
- **逻辑只在服务器上**：`next_step`，候选人页面看不到哪个答案会被筛掉。
- **配额**：`recruit.tiers_and_progress`，正式 / 备份按配额算；配额按 `tag` 或答案匹配。
- **匿名统计**：`RecruitForm.tally`，被筛掉的人只记匿名人数。
- **建议规则**：`recruit_review`，大部分建议靠规则算，不调模型；“采纳”才改，“不再提醒”会记下来。
- **翻译**：`recruit_translate`。

### 5.2 六步交互

左边按 6 步走，右边是问卷本身，确认一步就生成对应的题，新题短暂高亮。

| 步 | 左边显示什么 | AI 建议怎么来 | 确认后右边生成 |
|---|---|---|---|
| ① 读取立项 | 背景、目标、招募需求折叠成一条“来自立项”摘要，只读，“去立项改”能跳过去 | 不调模型 | 不生成题 |
| ② 要筛进谁 | 从招募需求拆出来的条件（品牌车主、保养渠道、购车时间、城市层级……），每条可勾选、改写，也可“自己加条件” | 模型只负责把招募需求拆成条件清单（JSON：条件、类型、选项建议）；服务器校验后显示；没有模型时按关键词规则拆，可能拆得粗 | 每个条件一道题：单选或多选，选项带“通过 / 终止”，选项的 tag 用条件名 |
| ③ 要筛掉谁 | 常见排除项清单：行业从业者（市场调研、广告、媒体、本品类）、近 3 个月参加过调研、不愿开摄像头或麦克风…… | 固定清单（放在 `constants`），按研究类型和访谈形式预勾；模型只补本项目特有的排除项 | 排除题：命中即终止；行业题放最前面 |
| ④ 配额 | 按 ② 的条件组合成配额表：组别 × 条件 × 人数；默认值来自立项第 4 步的配额表 | 不调模型，直接读立项配额表 | 不生成题；写进项目配额，“配额及受访者名单”页直接显示 |
| ⑤ 质量控制 | 可勾选：陷阱题（比如“请选第三项”）、前后一致性（两道题互相核对）、最短作答时长、重复参加识别 | 规则给默认：题数 ≥ 6 就建议加 1 道陷阱题 | 陷阱题、一致性题和服务器上的检查设置 |
| ⑥ 预览与测试 | 手机样式预览；“自己答一遍”，显示每一步走到哪、最后是通过还是终止、终止在哪一题 | 不调模型；测试走同一个 `next_step` | 不生成题 |

- **访谈形式不再问**：在立项里定。问卷末尾自动加的语言、形式、可约时间三题保留现状，是系统题。
- **每一步都能回退**：回退修改一步时，只重做这一步生成的题；其他步的题保留。如果后面某一步引用了被删掉的选项（比如配额引用的 tag），那一步标“需要重新确认”。

### 5.3 数据结构（在现有结构上加，不推翻）

- `Question` 加：
  - `step`：include / exclude / qc / system，记录这题是哪一步生成的，回退时据此只重做这一步；
  - `cond_id`：对应 ② 里的哪个条件；
  - `qc`：trap（陷阱题，`correct` 记正确选项编号）或 consistency（一致性题，`pair` 记互相核对的另一题编号和规则）。
- `RecruitForm` 加三列：
  - `plan_steps`（JSON）：6 步各自的状态（todo / confirmed / stale），以及 ② 的条件清单、③ 的排除清单、⑤ 的质控设置；
  - `qc`（JSON）：`{min_seconds, trap: bool, consistency: [...], dedupe: bool}`；
  - `step`（整数，取代现在作废流程用的 `stage` 1..11，旧值不再读）。
- **终止逻辑仍然只有一处**：`next_step`。在里面加：
  - 陷阱题答错 = 终止；
  - 一致性矛盾 = 终止，或标“可疑”留给研究员，由设置决定；
  - 最短时长：服务器记下第一题出现的时间（存在作答会话里，不信浏览器），提交时不足就终止。
- **重复参加识别**和 CLAUDE.md 的“被筛掉的人只计数不保存任何个人信息”冲突：要识别重复，就得留下被筛掉的人的某种标识。见第 9 节第 5 个拍板问题。

### 5.4 和“配额及受访者名单”的对接

- ④ 确认后写进项目配额：现在存在 `quotas` 的 JSON 列里，同一个数据结构、同一个函数（`validate_quotas`）。名单页的配额进度、正式 / 备份马上按新配额算，不用另外同步。
- ② 的条件名就是选项 tag，配额按 tag 匹配。改条件名会提示“配额里引用了它，一起改吗”。
- 立项第 4 步的配额表是默认值来源；在问卷里改了配额，和第 5 条一样提示要不要同步回立项（锁了就申请解锁）。

### 5.5 第 5 批的测试（到时候再细化）

`next_step` 逐条测（陷阱题、一致性、最短时长、回退只重做这一步）；配额写入后名单页的正式 / 备份；6 步走完生成问卷；回退修改；三种主题和手机预览截图。

## 9. 需要用户拍板的问题（6 个，每个附推荐）

1. **“qa.sh 全绿”怎么算？** 现在还没改，就已经有 11 个 pytest、110 条 qa_site、6 条 e2e 失败，而且 qa_site 和 e2e 会中途卡住（第 0 节）。
   - **推荐：先加一个“第 0 批”，把这些老失败修好或查明原因**（预计半天到一天），之后每批真正做到全绿。
   - 另一个办法：每批“和基线比不新增失败”，老失败单独列清单，后面再修。

2. **统一输入框的范围**
   - (a) 邮箱、数字、网址、搜索、CSV 粘贴这些框，用同一外观的“普通模式”（不加附件和语音），可以吗？
   - (b) 受访者端（招募问卷作答、访谈前问题、受访者房间回答框、异步研究）要不要也换？
   - **推荐**：(a) 可以；(b) 这一轮不换受访者端，只做研究员、管理员、客户、观察员、项目经理端。受访者页面另做效果图、单独确认，因为受访者端加语音要考虑同意和隐私提示。

3. **图片附件怎么处理？** 现在的模型只读文字，看不懂图片和截图。
   - **推荐：先接腾讯云的文字识别（OCR）**，把图里的文字交给 AI，卡片上写“只读取了图中的文字”。
   - 另一个办法：图片只保存、不读取，卡片写“AI 看不到图片内容”。
   - 接 OCR 要多开一个云服务，图片会发给腾讯云。

4. **大纲和子项目怎么对应？** 第 5 条要求“大纲对应到具体子项目”。
   - **推荐：一份大纲绑定一个子项目**（默认 S1，可以换），其他子项目先共用它；如果它们的形式、时长、语言和大纲不一致，就显示黄条。
   - 另一个办法：每个子项目各一份大纲（可从别的子项目复制）。改动大很多：看板、快照、直播间都要按子项目分开。可以以后再做。

5. **甄别问卷的“重复参加识别”**：要识别同一个人重复作答，就得留下被筛掉的人的某种标识，和现有规则“被筛掉的人只计数不保存任何个人信息”冲突。
   - **推荐：只对合格的人做重复识别**（他们本来就留了邮箱），被筛掉的人仍然什么都不存。
   - 另一个办法：对所有作答的人存一个加密打乱的邮箱摘要，30 天后自动删。这需要法务确认。

6. **发布门槛里，“暂缓”的标记、“暂不对应”的关注问题算不算已处理？**
   - **推荐：都算已处理，但在发布页显示数量**（“2 条暂缓、1 个关注问题暂不对应”），发布后在版本记录里保留。
